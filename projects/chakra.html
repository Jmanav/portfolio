CHAKRA

Cyber-Risk Engine for a Simulated Smart City — built and shipped an end-to-end cyber-risk ranking system for critical infrastructure (power, water, telecom, hospitals, transport), from threat-feed ingestion through a Monte Carlo attack/cascade engine to a FastAPI backend and React dashboard, containerized and deployed live.

Live Demo

dvd1906-cityrisk.hf.space — Hugging Face Space (sleeps after 48h idle; first request after a restart is slower).

Try: open the City map, run “Run the attack” on a flagged asset, then switch to Live detection to watch a replayed HAI/MSU telemetry feed shift the live threat level in real time.

Stages

1. Ingestion

  • Feed scripts (feeds/) fetch CISA KEV, FIRST EPSS, NVD and MITRE ATT&CK for ICS at dev time only, cached to data/feeds/ with a manifest (url, sha256, fetch date) — zero network calls at runtime.
  • A seeded generator (generator/build_city.py) builds a synthetic 90-asset city (RFC1918 addresses only, no scanning) with deterministic output: same seed → byte-identical city.

2. Processing

  • Assets, vulnerabilities and telemetry enter through three fixed seams (CityState.from_records, generator/vulns.py, ml/replay.py), so a new data source plugs in without touching engine code.
  • Two models (anomaly detector on HAI water-treatment telemetry, Random Forest on MSU/ORNL grid telemetry) convert recorded readings into likelihood-ratio evidence via a shared lookup table (engine/lr.py), gated by held-out metrics before either can emit a MODEL-badged number.

3. Core system

  • A pure-Python engine (engine/, zero imports from the API/web/ML layers) runs Monte Carlo attack simulation over the network graph, then a 24-hour time-stepped dependency cascade to compute person-hours of service lost.
  • Risk ranking uses marginal gateway value G(a) = CHAKRA − CHAKRA(a uncompromisable) with common random numbers, not CVSS score or summed per-asset risk — this is what lets the planner outperform a CVSS-first remediation order (99.9% vs 41.4% of modelled risk removed in the demo profile).

4. Evaluation / explainability

  • Every number returned by the API or shown in the UI carries a provenance badge (FEED, MODEL, GRAPH, ASSUMPTION, or SYNTHETIC) naming its source — enforced by a test that walks every API response.
  • An optional LLM explainer (off by default) is template-first; when enabled, a validator strips any sentence containing a number not present in the engine’s own output JSON, so the model can narrate but never invent a figure.

5. Output / delivery

  • FastAPI surface (api/) exposes assets, attack paths, cascades, uncertainty bands (P10/P50/P90), a remediation planner, live replay streaming (SSE), and an incident-report draft — all badge-walked and rate-limited.
  • A React + TypeScript dashboard (Vite, TanStack Query, Recharts) renders the city as an SVG map (no tile dependency), runs simulated attacks interactively, and shows a “why” chain per asset with zero client-side computation.

6. Deployment

  • Single Docker image: multi-stage build compiles the dashboard, precomputes caches at build time, and serves both API and static frontend from one uvicorn process on one port — verified to boot and serve with --network none.
  • Shipped to a public Hugging Face Space; CI runs lint, full test suite, and an offline boot test in Docker.

Architecture

Offline-first pipeline: dev-time feed caching → seeded generator → pure-Python scoring engine → FastAPI (badges everything) → React dashboard that only displays what the API returns.

Tech Stack

  • Language: Python 3.11, TypeScript
  • Backend: FastAPI, Pydantic v2, uvicorn
  • Engine: NumPy, SciPy, NetworkX, pandas, PyArrow
  • ML: scikit-learn (Random Forest), Isolation Forest, XGBoost
  • Frontend: React, Vite, TanStack Query, Recharts
  • API contract: OpenAPI (generated client/types)
  • LLM integration (optional): Anthropic Claude SDK, with output validation/grounding layer
  • Containerization: Docker, Docker Compose
  • Deployment: Hugging Face Spaces (Gradio host)
  • Testing: pytest, mypy (strict), ruff, Vitest, Playwright (E2E)
  • CI/CD: GitHub Actions

Limitations

  • Synthetic city only. All assets, addresses, and topology are generated; results describe this simulated city and its configured control strengths, not a real deployment.
  • ML models trained on foreign testbeds. The water and power models were trained on public industrial datasets (HAI, MSU/ORNL), not on this synthetic city’s own data — a deliberate choice to avoid training on self-generated labels, but it means domain transfer is unvalidated.
  • No AND-preconditions in the attack model (OR-only in this version) and the cascade ignores partial degradation and repair crews.
  • One known test gap: a replay-streaming test fails on Windows because it relies on a POSIX signal; unrelated to runtime behavior.
